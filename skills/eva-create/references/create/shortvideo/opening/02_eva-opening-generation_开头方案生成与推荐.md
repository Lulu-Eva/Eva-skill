## 输入边界

从 01 只承接：

- 场景：有标题开头 / 无标题第一句 / 只优化开头。
- 标题疑问或无标题主话题。
- 目标人群、用户问题和后文可兑现内容。
- 原开头最高优先级问题。
- 已确认可用事实、待确认信息和不可使用内容。
- 商单必提、禁区、不可承诺和可用真实素材。

缺少“材料放行：允许生成”或任一会改变事实边界的关键信息时，立即返回 01，不自行补猜。

## 数量协议

以下规则为稳定验收语义：

```text
内部候选池：至少 9 个，用于比较与淘汰
默认展示：3 个不同机制的候选，并从中推荐 1 个
发散 / 找灵感：展示 9 个，按 3 个不同机制分 3 组
显式 N：展示 N 个，覆盖默认 3 个或灵感 9 个
再来 N 个：保留已有候选，新增 N 个不重复切口，优先补未使用机制
保留 / 选择：只在已有候选中选择、组合或微调，不重跑候选池
沿选定方向再来 N 个：不重跑默认候选池，只在选定机制内新增 N 个实质不同切口
```

- “结果反差、结果先行、先报结果”属于同一机制，不能包装成三个方向；同一机制内的新增项必须更换事实入口、用户处境或叙事切口。
- 除非用户明确说“不用替我选 / 不要推荐”，推荐项必须从当轮展示项中选出；可以把它整理成可直接替换的前三句，但不能另造第 N+1 个方向。

## 候选机制

从下列六类中选择与当前话题匹配且有材料支撑的至少 3 类，不把清单全部展示给用户：

- 结果 / 反差：用已确认结果和直觉差异建立停留，可留下后文立即回答的原因缺口。
- 痛点 / 处境：说中目标用户正在经历的具体卡点，可用具体疑问打开小口。
- 教程 / 明确收益：只在正文确有步骤、方法、模板或收益时，预告真实会展开的过程。
- 反常识 / 转折：点破一个常见信念，并留下正文能解释的“为什么”。
- 真实素材 / 场景：从已提供的人物、动作、对话、过程或细节切入。
- 身份 / 资格：只使用已确认身份和表达资格，并让后文给出相应经验或证据。

“疑问 / 信息缺口”和“预告 / 过程”只是上述六类的具体写法，不单列为一级机制。灵感模式优先使用有支撑的结果、痛点、教程三组；缺支撑时改用其他机制，不凑固定公式。

## 生成过程

### Phase 1：内部生成

- 至少生成 9 个候选，覆盖至少 3 种机制。
- 每个候选都要能追溯到 01 给出的标题疑问、主话题、已确认事实和正文承诺。
- 不向前台输出被淘汰候选、打分表或内部推理过程。

### Phase 2：硬边界淘汰

命中以下四类任一项就淘汰：

1. **事实与结果越界**：新增数字、身份、经历、评论或结果；把“收到面试邀请”升级成“拿到 Offer”；把单一案例写成普遍保证。
2. **因果越界**：把时间先后或相关性写成“因为 A 所以 B”。
3. **教程承诺越界**：正文无依据却新增教程、模板、步骤、时长或收益承诺。
4. **Brief、标题或正文不兑现**：触碰商单必提、禁区或不可承诺；小红书改变标题主疑问或绕过标题验证；抖音/视频号第一句不能独立交代话题、停留理由和兑现线索；开头承诺正文不展开。

只换同义词、主语、句序或标点不算新候选，回 Phase 1 更换机制或实质切口。

如果淘汰后不足用户要求的数量，继续生成新候选并执行同一轮硬边界检查；不能为了凑数降低边界。

### Phase 3：排序与推荐

按以下顺序选出前台候选：

1. 事实和 Brief 安全。
2. 与标题疑问或无标题主话题对位。
3. 后文能直接兑现，不需要正文硬圆。
4. 目标用户能立即确认“这在说我”。
5. 候选之间机制有实质差异。
6. 第二、三句能自然承接，口播念起来顺。

默认展示 3 个时，在通过上述排序后再执行一次机制去重：每个展示项只能占用一个机制类别，三个展示项必须是三个不同类别。灵感模式则以三个不同机制分组，组名和实际切入方式必须一致。

推荐不只看“最炸”，而是选事实最稳、承接最顺、后文最能兑现的一个。

## 前台输出

### 默认优化

```markdown
## 我先只看开头

最高优先级问题：

## 3 个开头方案

### 1. [机制名]
（第一句 + 必要的前三句承接）

### 2. [机制名]
（第一句 + 必要的前三句承接）

### 3. [机制名]
（第一句 + 必要的前三句承接）

## 我最推荐
- 推荐：第 X 个
- 可直接替换的前三句：
- 理由：

## 下一步
- 动作：
```

三个方案必须是三个不同机制；“我最推荐”只能从中选定并整理，不能新增第 4 个方向。

### 发散 / 找灵感

```markdown
## 9 个开头灵感

### 第一组：机制名
1.
2.
3.

### 第二组：机制名
4.
5.
6.

### 第三组：机制名
7.
8.
9.

★ 最推荐：
理由：

## 下一步
- 动作：
```

每组必须是不同的表达机制，组内候选也必须是不同切口，不用 9 个近义句凑数。

### 用户指定数量

```markdown
## N 个开头方案
1. [机制名]（第一句 + 必要承接）
2. [机制名]（第一句 + 必要承接）
...
N. [机制名]（第一句 + 必要承接）

★ 最推荐：第 X 个
理由：

## 下一步
- 动作：
```

标题与列表都必须等于用户指定的 N。N 大于 3 时可按机制分组，N 较小时不为分组凑数；用户拒绝推荐时删去推荐段，否则推荐必须来自这 N 个，不计作第 N+1 个。

## 风格与边界

- 只在用户已提供原稿、voice-card 或明确当轮语气指令时，做个性化节奏保护；不凭空推断长期文风。
- 不把 Eva 的互动语气写入用户稿件，不硬塞固定口头禅。
- 只优化开头时，不默认重写完整正文。
- 开头已经成立时，允许建议保留原版；不为了证明会写而强行换掉。
- 用户要完整稿时交回 `/eva-script`；小红书标题未验证先回 `/eva-title`，抖音/视频号可用已放行的无标题第一句继续交接。
- 最终只给一个下一步动作。
